# Issue 71: HTTPS managed kiosk acceptance

Based on PR #70 `3b71ddbf2c20141f2849d711e8c77a8d6c2fc7e8`. No schema change or Migration. Existing device TokenHash is the server revocation record. No agent is installed and no production directory/database is modified by this PR.

## Deployment prerequisite (test in an isolated directory first)

- Serve the production client and `/api` through **one HTTPS origin**, with a certificate trusted by the actual playback browser. Set `DASHBOARD_PUBLIC_CLIENT_ORIGIN=https://your-managed-host[:port]` (no trailing slash, credentials, path, query or fragment). No origin is guessed from request headers or development ports.
- Set `DASHBOARD_KIOSK_COOKIE_KEY` to a dedicated random 32-byte key, encoded as 64 hex characters. Provision it using your secret manager; keep it stable across process/reboot/deployment and consistent across API instances. Do not reuse JWT/DataSource keys or include it in bundles/logs/source. Rotation invalidates all enrollments and sessions. Existing device/query feature flags must also be enabled.
- For TLS termination, enable existing `TRUST_PROXY_ENABLED` only with exact `TRUST_PROXY_ADDRESSES` of the controlled proxy. Restrict the API port to that proxy; strip incoming `X-Forwarded-*`, overwrite `X-Forwarded-Proto: https`, preserve the public Host, and set the actual client address in `X-Forwarded-For`. Never trust arbitrary clients/subnets. Direct TLS is also accepted. IP resolution continues through existing `getClientIp`; an untrusted sender cannot override the socket address.
- Send HTTPS/HSTS, `Cache-Control: no-store` for playback HTML/API, `frame-ancestors 'none'`, `object-src 'none'`, and a production script CSP allowing only required same-origin scripts (no inline script/eval). Do not cache `/api` or install a service worker for patient data. The API already uses Helmet. Deploy the built client, not the Vite development server.

## Authorization and lifecycle

The device URL contains only dashboard ID and `deviceId`; several devices may share a dashboard. A URL is **not** authority. On the intended browser/profile, input the one-time Token and leave “在此瀏覽器持久授權裝置” selected. Wrong-device Tokens are rejected. No persistent fallback is attempted on HTTP, missing configuration, insecure proxy, invalid mode or policy.

The server puts an AES-256-GCM authenticated/encrypted envelope in a `__Host-uqp-enrollment-{deviceId}` **HttpOnly, Secure, SameSite=Strict, host-only, Path=/** persistent cookie. It is bound to HTTPS origin, purpose, device, dashboard, mode revision and expiry. The credential is never returned from enrollment/restore. Browser JS cannot read the cookie and no plaintext Token is written to browser storage, URL or launcher. A dedicated key is required; there is no predictable fallback key. The cookie lifetime is capped by the original device expiry and 365 days, never silently extended by restoring. A device renewal beyond that enrollment limit requires explicit enrollment again.

A separate similarly protected session cookie lasts at most five minutes and never beyond device/enrollment expiry. The client restores/renews it with a JSON POST and performs the existing playback verification every 15 seconds (independent of page intervals). Every cookie-authenticated layout/page request also rechecks device status, token hash (reissue invalidates old cookies), expiry, IP, workstation, delegator authorization/revision, mode/grant version, and existing PRIMARY Query ACL/Dataset/public policy inspection. Existing page/source execution retains its additional live checks, masking and patient disclosure audit **before** delivering rows. Session creation/restore runs no clinical query and produces no patient rows.

Cookie API requires the configured Host and HTTPS, a custom `X-UQP-Kiosk` request marker, and same-origin Origin on POST; cross-site fetch metadata is rejected. Read-only GET layout permits omitted Origin (browsers omit it), still requiring the custom marker, same-origin/absent fetch metadata and short session. Such custom headers require a cross-origin preflight; existing CORS and Origin checks prevent cross-origin credentialed reads/writes. No GET enroll/restore, URL credentials or cookie-to-Legacy fallback exists. Headers/cookies retain existing logger redaction; errors are static and do not echo credential/SQL/policy internals. Audit receives no Token/cookie. HttpOnly mitigates secret extraction, **not** the ability of same-origin XSS to operate an authorized browser: production CSP, trusted scripts and managed OS/browser profile remain necessary. OS profile compromise is outside browser cookie isolation.

Authorization failures clear both cookies when the trusted device is identified. Observed failures with an authenticated grant also evict that device’s patient snapshots in the receiving API process; failed unauthenticated requests cannot evict another device’s snapshots. Existing caches are process-local, so another API instance evicts on its own verification/TTL; every instance still validates before returning any rows. Client clears primary/supplemental patient rows, layout, snapshot IDs and pending generations on failure, server lease deadline, offline transition or pagehide. Back/forward restore reloads and revalidates rather than displaying old snapshots. Revocation is noticed by the next request or the independent recheck (up to 15 seconds while online), not an instantaneous server push. No automatic retry can revive a revoked/expired/reissued grant. “清除此瀏覽器持久授權” deletes local cookies; it does not revoke another browser's server grant. Use administrator revocation/reissue to invalidate all copies. A copied cookie is a bearer credential; do not export browser profiles or Playwright storage state to another device.

Existing once-only Token reveal/copy and optional window handoff remain available as one-page authorization. They do not silently opt a device into persistence. Sensitive enrollment POST bodies must not be captured by reverse-proxy/body logging or APM.

## Playback URL and Windows BAT

After metadata/placement save, the device list automatically displays the server-configured URL; it also provides show/copy/open/download controls. URL copy/open remain explicit user actions (clipboard and popup browser restrictions). Without valid public HTTPS configuration, links/launchers are unavailable; there is no localhost or HTTP guess.

Download BAT **after saving placement**. It contains only public URL/device ID and saved placement. Its PowerShell EncodedCommand prevents CMD quoting/percent expansion; this is not secret storage. It discovers Edge/Chrome in Program Files (x86/x64) and LocalAppData; errors are visible. It uses a dedicated durable `%LOCALAPPDATA%\UQP\Kiosk\<origin-hash>\device-<id>` browser profile. **First enrollment must happen in the window launched by this BAT**, not an administrator/default browser profile. Reuse the same Windows user, browser, profile and public origin after reboot. Do not use InPrivate/incognito or Edge `--kiosk` mode, which can delete cookies on exit. Do not clear cookies with enterprise exit policies.

`screenNumber` is the 1-based index of `Screen.AllScreens` sorted by Windows `DeviceName`; it is **not** a stable EDID/display-settings number. A missing configured screen stops launch. Saved X/Y are absolute desktop coordinates and may be negative; when outside the selected screen the launcher uses that screen's top-left. Width/height apply to a window; fullscreen uses `--start-fullscreen`. Fullscreen dimensions follow the selected monitor. Windows scaling/DPI, monitor hotplug/order, running browser processes and browser flag behavior need physical acceptance. BAT is not a Window Management API permission grant.

For automatic launch after reboot, create a managed **interactive logon** Task Scheduler/Startup entry for the BAT using the same Windows account. Do not run as SYSTEM or before interactive logon (no visible desktop). Configure any automatic Windows logon separately under your organization's kiosk policy; this PR does not change OS credentials or logon security. Do not put Tokens into the task, arguments, BAT or shortcuts.

## Isolated acceptance procedure / PASS versus BLOCKED

1. Provision HTTPS origin/proxy and dedicated key in an isolated installation; verify direct HTTP, false forwarded HTTPS, foreign Origin, wrong Host and missing key all refuse persistent enrollment.
2. Use a synthetic masked Dataset and configured disclosure audit. Save two devices for the same dashboard; verify public URLs identify them and contain no secret. Save each browser/monitor/position/size/fullscreen option, download BAT, inspect its decoded script (public URL/config only).
3. Launch BAT on Windows Edge/Chrome and paste the intended newly issued Token once. Verify masking and patient disclosure audit. F5, close all browser windows/processes, reopen BAT, then cold boot Windows and log on/start task. Verify playback restores from the same profile without input. Repeat left/negative-coordinate and mixed-DPI monitors. **This physical Windows reboot/monitor/fullscreen acceptance is BLOCKED until user confirmation.**
4. Test revoke, expiry, Token reissue, wrong device ID, IP/proxy change, delegator permission/revision/Query ACL change, Query-only revision/mode/flag change, masking/public policy change, audit write failure and network outage. Verify no rows on a failed check and purge of existing display; old authorization never resurrects after restart. Restore only with explicit valid enrollment when needed.
5. Verify no Token in URL/localStorage/sessionStorage/BAT/logs/Audit or document.cookie; enrollment input disappears on successful activation. Confirm cookie flags in browser settings; don't export values. Clear local enrollment and confirm restart asks for input. Confirm original one-time reveal and optional handoff still behave as before.

Automated tests cover real Chromium process/profile restart and secure-cookie persistence with a real HTTPS synthetic API (ephemeral self-signed test certificate, browser trust explicitly relaxed only in tests), not Windows boot or a live SQL Server/Oracle. Server CI uses no real database. Android Chrome / iOS Safari can use the implemented HTTPS same-origin cookie/manual-enrollment flow in a normal persistent profile; private browsing, cookie eviction, PWA/managed kiosk lifecycle, mobile OS restart and fullscreen behavior are **not hardware-validated**. Windows BAT is Windows-only; no mobile launcher/agent is provided. Pure HTTP unattended persistence is unsupported and remains fail-closed.

Ready to download sources for **isolated local acceptance after CI passes**; not a production rollout approval. No SQL changes are required by this PR, and no Migration or update package was executed/generated.
