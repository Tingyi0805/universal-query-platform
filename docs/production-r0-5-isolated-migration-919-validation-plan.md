# UQP R0-5｜獨立 SQL Server Migration 919 驗證計畫

> 狀態：**PREPARATION ONLY / NOT RUN / NOT AUTHORIZED FOR PRODUCTION**。本文件只規劃驗證，不提供對正式或共用 SQL Server 執行 Migration 的授權。不得將正式憑證、備份、病患資料複製至測試環境。

## 1. 環境邊界與開始條件

- 使用**獨立 SQL Server 實例**（不同於正式 SQL Server 及同實例 `UQP_TEST`）；獨立儲存空間、測試帳號、網路連線設定、備份及恢復程序。
- 由現場管理者確認實際實例／資料庫／登入身分，並取得明確的**測試實例執行授權**。測試應用程式也不得觸及正式 HIS、Oracle、設備與通知端點。
- 以 GitHub 固定 Commit SHA、SHA-256 migration inventory 與審查過的合成資料建立測試基準；不直接複製正式患者資料或正式 SQL 備份。
- 測試環境先安裝／驗證 001–026、900–915，並對照正式已盤點的 915 Schema 要求；記錄測試基準的 SchemaMigration 與結構指紋。
- 對每一測試案例使用**新的可重建資料庫或核實還原點**，避免前一案例影響下一案例。
- **禁止**以 `npm run db:migrate`、`db:migrate:status`、`adopt` 直接測試正式或共用實例；既有 Runner 預設執行所有未安裝 Migration，沒有指定只執行 919 的白名單。

## 2. 驗收案例與證據

| 案例 | 驗證步驟（僅限核准後的獨立實例） | 通過標準 |
| --- | --- | --- |
| M919-01 基準 | 核對測試 915 ledger、欄位、約束、索引 | 達到 915 基準且無 916–919 部分殘留 |
| M919-02 正常安裝 | 從乾淨 915 基準執行**受控且僅含 919**的測試執行路徑 | 新版本欄位、rowversion、Metadata 表、CHECK／FK／PK 正確，ledger 僅新增預期項 |
| M919-03 前置缺失 | 在合成測試副本移除／改變指定前置物件後測試拒絕 | 正確失敗、沒有成功 ledger、無不預期殘留 |
| M919-04 類型衝突 | 在合成測試副本製造 ConfigurationVersion／ApprovalRowVersion 衝突 | 拒絕修改，保留失敗前狀態 |
| M919-05 內部交易失敗 | 以可還原副本測試 919 中途異常與 XACT_ABORT／ROLLBACK | 表、欄位、約束與 ledger 回到測試前一致狀態 |

| M919-07 重複與漂移 | 測試再次安裝、部分安裝及同名不同語義的約束 | 不誤判已完成；不覆寫未知結構 |
| M919-08 舊資料相容 | 合成 Dashboard、Dataset、Query、裝置／患者稽核設定前後比對 | ID、綁定、設定、權限、既有業務資料均保留；不自動認證患者 Metadata |
| M919-09 新版功能與稽核 | 合成帳號執行版本衝突、權限拒絕、稽核失敗與回滾 | fail-closed；無明文患者資訊；無部分提交 |
| M919-10 回復演練 | 從核實的**測試專用備份**還原與重新盤點 | 服務與資料可恢復到明確的基準，記錄耗時和負責人 |

## 3. 實施原則

- 第一階段先產出**唯讀**的 SQL Server 身分、Schema 與 ledger 證據，不執行任何 DDL/DML。
- 只有在獨立實例身分、合成資料、快照與執行者授權均確認後，才另行設計**僅限定測試實例**的 allowlist runner／故障注入程式；不得讓測試入口自動讀取正式環境設定。
- 成功與失敗案例分開保存：固定 GitHub SHA、測試實例識別碼（內部保存）、前後 Schema／ledger 對比、操作紀錄、錯誤碼、耗時、還原證據。不得輸出機密連線字串或真實患者資料。
- 若發現連線指向正式或共用實例、測試帳號具備正式 DB 權限、未預期跨系統呼叫、備份不可還原、Schema/ledger 漂移，**立即停止**。
- CI／Mock／靜態審查即使成功，以上案例仍標示 `NOT_RUN`，不得表示已驗收。
